# C4 Views and Security Overlays Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add optional C4 presentation, application/context views and evidence-based identity/network overlays.

**Architecture:** Preserve the graph → renderer-independent views → D2 pipeline. Keep authorization evidence separate from resource nodes, use explicit resource-to-view projections for aggregation, and render only cached evidence.

**Tech Stack:** Python 3.12+, argparse, dataclasses, PyYAML, pytest, D2 with ELK.

**Spec:** `docs/superpowers/specs/2026-10-29-c4-security-design.md`

## Global Constraints

- Keep Python 3.12+, D2 with ELK, and existing dependencies.
- Rendering remains offline from caches.
- Default `--view all` retains detailed and summary; default style is `azure`, overlay is `none`.
- Preserve existing default filenames and use distinct filenames for variants.
- Unknown never means no access; grants do not establish exclusive access or observed usage.
- New application/context views may combine selected subscriptions; existing views/reports stay per subscription.

## Review Focus

- Identical application tags in different environments/subscriptions must remain separate unless overridden (Task 3).
- Shared or multiple identities must not create invented workload authentication claims (Tasks 2 and 4).
- Resource-group/subscription grants and conditions must retain scope and coverage caveats (Tasks 2 and 4).
- Summary collapsing must not discard identities, provenance or security differences (Task 4).
- Old caches and failed/partial security reads must permit ordinary renders and visibly qualify overlays (Tasks 1 and 5).
